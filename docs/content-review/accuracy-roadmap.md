# Roadmap (roadmap.html) vs JanusV7 — accuracy review

## Accurate / well-supported
- **Phase 1 — Private Beta: "governed workflows, institutional memory, deterministic gates"** — this is exactly what's implemented today: `workflow_contract.py`, the 5-outcome gate model, and the L1 memory vaults are live and tested (190+ backend tests per `AGENTS.md`).
- **Phase 1 — "agents, workflows, and gates are informed by your company documentation — ingested, structured, and curated from day one"** — matches `company_documents/README.md` (hygiene cards reference real files; gates treat a card as filed when the file exists and is non-empty) and the DTM hygiene ingestion pipeline (`make dogfood-ingest-hygiene`).
- **Correctly framing Phase 2 ("Arbiter"), Phase 3 ("Toth"), and Phase 4 ("Thought as Data") as *not yet shipped*** — this positioning is directionally honest; none of these exist as production features today (see below for nuance on how far along each actually is).

## Needs update / caution
- **Phase 2 — "The Arbiter": described as future work, but it's further along than "roadmap" implies.** There is already a dedicated, working dogfood surface for it: `frontend-arbiter/` ("Arbiter Dogfood — Intent Hardening"), with its own README and findings doc (`frontend-arbiter/FINDINGS.md`). Also, per `docs/JANUS_RITUAL_CLI.md`: *"in product language you may call that voice an 'Arbiter' mirror; in doctrine the first gate in the six-agent pipeline is Caretaker — there is no separate nano-agent symbol named Arbiter in code unless one is added later."* In other words, "Arbiter" today is (a) a product-language alias for the existing **Caretaker** agent, and (b) an active internal dogfood prototype — not a brand-new, unbuilt capability. Recommend clarifying that Arbiter builds on/relabels existing Caretaker intent-gating rather than implying it starts from zero in Phase 2.
- **Phase 3 — "Toth": exists only as an archived/experimental stub, not as scoped, active roadmap work.** The only code hits for "Toth" are in `backend/systems/_archive/arbiter.py` (an *archived* file) with comments like `"Mocking Toth check for now - in real v7 this queries the inbox"` and a `DRIFT_REVIEW` state labeled `(Toth)`. There's also a mention in a discovery/portfolio note (`vaults/stmvault/discovery/portfolio/2026-07-16_discovery_process_reflections.md`) about "Reintroducing Toth with a vector living in parent cards" — i.e., it's currently a discovery-stage idea being revisited, not built infrastructure. The roadmap position (Phase 3, after Arbiter) is fine, but the page's confident forward-looking language ("the system begins to see what a single operator cannot see") should not be read as reflecting any current implementation — it's pure concept today.
- **"Phase 2.5 — Coaching and Delta Analysis"** — some of this already exists in early form: `cli/mc_bin_coaching_prompts.py`, "coach MC" scoring in `vaults/ltmvault/doctrine/workflow_contract_v1.md`, and `.cursor/rules/06-dogfood-delta-record.mdc` describe a working delta-record/coaching mechanism today, ahead of where "Phase 2.5" (after an unbuilt Phase 2) might suggest. Consider whether this phase ordering still matches reality, since coaching/delta scaffolding appears to already be partially live.

Appears to be a purely aspirational, far-future vision statement; nothing to fact-check, and nothing contradicts it. Fine as vision language as long as it isn't implied to be scheduled/in-progress.
